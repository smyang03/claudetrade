# 설계·토론·검증 — KR 브리지 합집합 규칙(R2∪R4) 지원 (2026-08-10)

목적: Phase 2(사전등록 v2 사다리) 승인 당일 "두 소스 플래그 전환 + 재시작 + 실측"만으로
발동 가능하게, 합집합 active_rule을 **기본 OFF(현행 R2 유지)** 상태로 사전 구현한다.
이 문서는 구현 전 설계·토론·코드 대조 검증 기록이다.

## 1. 현행 코드 실측 (설계 입력)

- `KR_FALLEN_ACTIVE_RULE` env 단일 문자열(기본 "R2"), 두 소스 규칙 적용 대상.
- `runtime/kr_fallen_order_bridge._rule_key()`: R1/R2/R3/R4 → 단일 규칙 키 매핑.
  `_load_candidates()`가 단일 키로 원장 필터 후 ma20_disc 오름차순 정렬.
- 규칙 판정은 `tools.kr_fallen_gate_report.rule_flags` **공유**(정의 단일화 원칙 기존 준수).
- 한도: 일1건(`KR_FALLEN_MAX_NEW_PER_DAY`)·슬롯(`KR_FALLEN_MAX_OPEN_SLOTS`)·30만·
  극단 갭업 가드·공통 매수 게이트 — 전부 규칙과 독립.
- ⚠️ 발견: 게이트 리포트 `[랭킹]` 뷰도 status의 active_rule을 **단일 키로 파싱** —
  합집합 문자열이 오면 조용히 R2로 폴백한다. 브리지만 고치면 관측이 어긋난다.

## 2. 설계

**D1. 표기**: `KR_FALLEN_ACTIVE_RULE="R2+R4"` — 구분자 `+` 또는 `,`, 공백 무시,
대소문자 정규화. 토큰 ⊆ {R1,R2,R3,R4}. 의미 = 토큰 중 **하나라도** rule_flags 충족.
**D2. 파서 단일화**: `parse_active_rules(raw) -> tuple[str,...]`(정규 키 목록)를
`tools/kr_fallen_gate_report.py`에 신설 — 브리지와 리포트 [랭킹] 뷰가 **같은 파서**를
import (1항의 어긋남 방지, rule_flags 공유 원칙과 동일한 구조).
**D3. 무효 토큰 = fail-closed + loud**: 알 수 없는 토큰이 있으면 후보 0 +
`status=ERROR_INVALID_ACTIVE_RULE` + log.error. **조용한 R2 폴백 금지** — 오타가
"레인이 소리 없이 구식으로 도는" 지뢰가 된다(임의 해석 금지, A1 셧다운 계열 교훈).
아침 status 파일에서 즉시 보인다.
**D4. 매칭 태그 기록**: 핸드오프 결과의 후보별 details에 `matched=["R2"]/["R4"]/둘 다`
기록 — 판정 시 R4∖R2 순증분 분해(사전등록 요구)를 이력 원장에서 직접 복원.
**D5. 불변 항목(명시)**: 정렬(할인깊은순)·일1건·슬롯·사이징·갭업 가드·게이트·계약
전부 무변 — Phase 2는 선별 확장이지 용량 확장이 아니다.

## 3. 토론 (쟁점과 결정)

- **새 단일 키 "R5"로 명명?** → 기각. 사전등록 문서가 "R2∪R4"로 명명했고, 감사 시
  구성 문자열이 자기 설명적("R2+R4")인 쪽이 오독이 없다. 조합 일반화도 공짜로 얻는다.
- **무효 토큰을 R2로 폴백?** → 기각(D3). 가용성보다 가시성 — 폴백은 전환 실수를
  몇 주 뒤 판정 때 발견하게 만든다. fail-closed는 다음 아침 status에서 바로 잡힌다.
- **겹침(R2∩R4) 우선 정렬?** → 기각. E5 실측에서 겹침우선(V2)은 연도 갈림 —
  랭킹 변경 근거 없음. 할인깊은순 유지.
- **R4 단독 전환(R2 제거)?** → 기각. R2는 통과 시 최상급(+5.95/건)이고 침묵은 국면
  문제 — 버릴 이유가 없다. 합집합이 사전등록안 그대로다.

## 4. 검증 (엣지 케이스 대조)

| 케이스 | 판정 |
|---|---|
| 후보가 R2·R4 동시 충족 | 단일 행에 any() — 중복 진입 없음. matched에 둘 다 기록 |
| 기존 "R2" 단일 문자열 | tokens=("R2",) — **현행 동작과 바이트 동일해야 함(테스트로 고정)** |
| "R3+R4" 같은 미사용 조합 | 의미상 유효(R1∪R2∪R4) — 허용하되 쓸 일 없음 |
| [랭킹] 뷰의 합집합 status | D2 공유 파서로 해소 (미수정 시 조용한 관측 어긋남 — 이번 검증의 실질 수확) |
| 이력 원장 서명 중복 억제 | rule 문자열이 서명에 포함 — 전환일 새 서명, 정상 |
| 리허설 도구 | `--rule "R2+R4"` 시나리오 추가 필요 (18/18 통과 기준 유지) |

## 5. 테스트·전환 절차 (구현 시 포함)

- 단위: R2-only 히트 / R4-only 히트 / 동시 히트 / 무효 토큰 fail-closed / 단일 "R2"
  후방 호환 / 정렬 불변 — `tests/test_kr_fallen_order_bridge.py` 확장.
- 리허설: `kr_fallen_handoff_rehearsal --rule "R2+R4"` 통과.
- 전환 체크리스트(승인 당일): 두 소스 동시 `R2+R4` → 안전창 재시작 → effective-config
  실측 → 익일 status.active_rule 확인 → 첫 판정 reason 확인 → 첫 실주문 matched 태그 확인.

구현 전까지 라이브 동작 무변(기본 "R2"). 구현 후에도 전환은 게이트+운영자 승인으로만.
