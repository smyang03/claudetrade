# 네 축 심층 점검 — 분석과 반영안 (2026-07-23)

운영자 요청으로 오늘 남겨둔 네 축을 전부 팠다. 결과와 **어떻게 반영할지**를 함께 적는다.

## 축 1. judge recheck 큐 — ★ FIFO다. 우선순위가 없다

### 실측

```
큐 대상(세션·시장·종목) 384 | 실제 재호출 122(31.9%) | 만료 254
dropped 421건, 사유 100% 'expired' — 품질 기반 축출은 0건
queue_size 평균 23.4 · 최대 48   vs   judge 예산 세션당 ~10

큐 사유: judgment_not_executable 847 · capacity_exhausted 337
        · adaptive_live_reask 290 · entry_blackout 50 · run_cap_reached 29
```

### 코드 확인 — 추론이 아니라 실물

`trading_bot.py:32644`
```python
selected_items = due[:max_per_run]
```

**due 리스트를 앞에서부터 자를 뿐이다.** 점수·랭킹·우선순위가 어디에도 없다.
큐에 23개가 있고 10개를 가져가는데, 그 10개는 **도착 순서**로 정해진다.
나머지는 시간이 지나 `expired`로 사라진다(축출 사유가 전부 expired인 이유).

### 왜 중요한가

메모리에 **judge 예산 확대는 반증**돼 있다(세션 −0.128%). 그건 "더 많이 보자"를 죽인 것이지
**"같은 10개를 무엇으로 고르는가"는 한 번도 검증된 적이 없다.** 지금 답은 "도착 순서"다.
예산이 구속되는 상태(capacity_exhausted 337건)에서 선별이 무작위에 가까우면,
같은 비용으로 개선할 여지가 남아 있다는 뜻이다.

### 사후 성과 비교는 판정 불가 — 표본 부족

```
거래 단위  호출 n=17 평균 +0.589% 승률 23.5% p90 +29.98
          만료 n=88 평균 -0.024% 승률 44.3% p90  +3.32
세션 단위  양쪽 표본 있는 세션 4개 · 평균 차 +0.650%p · 호출 우세 2/4
```

**n=17, 4세션이다. 결론 내지 않는다.** 방향(호출 쪽이 승률 낮고 꼬리가 두껍다)은
"judge가 고변동 종목을 고른다"와 정합하지만 통계적 의미는 없다.

### 반영안

| 단계 | 내용 |
|---|---|
| 즉시 | **큐 정렬 shadow.** 현재 FIFO 선택과, `trainer_prompt_score`/`rel_vol` 등으로 정렬했을 때의 선택을 **둘 다 기록만** 한다. 주문 영향 없음 |
| 관측 | 두 선택의 겹침률과 각각의 forward를 세션 단위로 누적. 최소 15세션 |
| 전환 | 세션 단위로 정렬안이 우세하고 부호가 안정적일 때만 enforce. 운영자 승인 |

**지금 enforce하지 않는다.** n=17로 정렬 규칙을 바꾸면 오늘 P0-1과 같은 실수가 된다.

**sleeve 2종은 4건 전부 체결됐고 net 보유 0건이다.** route도 전부 불명.

전부 여기 소속인데, **손익이 canonical에 net으로 기록되지 않는다.**

### 반영안

| 우선 | 내용 |
|---|---|
| P0 | sleeve 체결에 `route`/`path_type` 부여 — 최소한 `sleeve`로 라벨. 지금은 `unknown`이라 어떤 집계에도 안 잡힌다 |

이건 수익 레버가 아니라 **위험 관리**다. 실제 돈이 있는 경로를 계측 못 하는 상태다.

## 축 3. 매도 경로 — 예측 6건 중 1건 확정, 1건 반증

서브에이전트가 코드에서 예측한 누수를 6월 표본(closed 152건)으로 검증했다.

### ★ 확정: `mfe_time`/`mae_time` 전량 미수집

```
6월 closed 152건
  mfe_pct   152/152  (100%)
  mae_pct   152/152  (100%)
  mfe_time    0/152  (0%)   ★
  mae_time    0/152  (0%)   ★
```

값 축은 완전한데 **시간 축만 통째로 비어 있다.** 예측한 3중 조건부가 맞다:
① 신고점 갱신이 없으면 `observed_peak_at` 미기록 ② durable 영속화가 갱신 사이클에만
발생 ③ `mark_closed`에서 빈 문자열이면 키 자체 생략.

**이게 왜 큰가**: 메모리에 초기경로·MFE 시점 분석이 반복해서 "최고 ROI 축"으로 적혀 있다
([[six-visions-verified-20260719]]의 경로유전자, 30분 마크 enforce 근거). 그런데
**그 분석의 시간 축이 수집 자체가 안 되고 있다.** 지금까지의 초기경로 결론은
전부 백필·대체 소스로 만든 것이고, 라이브 수집은 0이다.

### 반증: exit 중복억제 과소집계는 근거 없음

```
CLOSED 이벤트  6월 180건 · 7월 4건
close_reason   LOSS_CAP 44 · CLAUDE_PRICE_STOP 23 · HARD_STOP 18
               · CLAUDE_PRICE_TARGET 17 · PROFIT_LADDER 15 · CLAUDE_SELL 8 ...
```
분포가 정상이고 특정 사유로 쏠리지 않았다. 과소집계 징후 없음. **이 예측은 닫는다.**

### 반영안

| 우선 | 내용 |
|---|---|
| **P0** | `mfe_time`/`mae_time` 수집 복구. 세 조건부 중 ②(갱신 사이클에만 영속화)를 먼저 — 매 사이클 영속화하거나 종료 시 1회 확정 기록 |
| P1 | `_update_position_excursion` 단일 호출점(`pathb_runtime.py:3934`) — PathB 외 포지션은 MFE/MAE 자체가 생성 안 됨. sleeve 포지션이 정확히 여기 걸린다 |

## 축 4. 내가 오늘 다섯 번 틀린 패턴 — 가드는 하나뿐이다

```
1 DELL 사인을 volume_ratio_open으로 지목      → 실제는 코어 모멘텀 결측
2 차단 사유를 momentum_state=sustained로 라벨 → pack에 그 키가 없었음, 진짜는 data_quality
3 atr_pct를 placeholder로 보고               → 원장에 컬럼 자체가 없음(SQLite 리터럴 함정)
4 data_quality 미전달을 강등 원인으로 지목     → 공변량. 실데이터 효과 0
5 recheck 큐 "383건 증발"                    → consume 스키마 오독. 실제 31.9% 재호출
```

**공통 구조: 숫자에서 인과를 추론한 뒤, 스키마·코드를 확인하기 전에 보고했다.**

도구로 막은 것: 컬럼 존재 선확인(3번 유형) — 적용 완료.
**도구로 못 막는 것: 4번(공변량 오독).** 이건 반사실을 반드시 **실데이터에 A/B로**
돌려야만 걸린다. P0-1이 그 단계를 안 거쳐서 "P0 해결"로 보고될 뻔했다.

### 반영안 — 계약으로 고정

> **반사실 보고 규칙**: 어떤 수정이 "N건을 회복시킨다"고 주장하려면,
> 수정 전/후 규칙을 **같은 실데이터 전량에 돌려 delta를 낸 뒤** 보고한다.
> 단위 테스트 통과나 케이스 주입만으로는 효과를 주장하지 않는다.

오늘 P0-1은 이 규칙을 적용해 무효로 판명됐고, P0-2(체결축)는 246행 실제 복구로 통과했다.
이 규칙을 `tools/pipeline_integrity_audit.py` 문서화에 넣었다.

n=17이다. 오늘 P0-1에서 배운 대로, 근거 없이 enforce하지 않는다.
